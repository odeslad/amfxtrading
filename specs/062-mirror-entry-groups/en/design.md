# 062 — Mirror entry groups · Design

> Status: **approved**

## Approach

A group is a set of `(broker, ticket)` pairs plus a colour, stored in the backend. It is created by the backend itself when the commands of one mirror send come back with their tickets, so it does not depend on the browser staying open. Propagation stays in the frontend, which already sends one command per entry (the edit and close panels take lists): an action on a grouped entry is expanded to every open entry of its group before sending. The EA ↔ backend contract does not change.

An MT4 pending order keeps its ticket when it fills, so AC 8 comes free.

### Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| **A. Backend creates the group from the command results (chosen)** | Works even if the tab closes before the tickets arrive; one source of truth | `POST /commands` gains an optional field |
| B. Frontend waits for the tickets and posts the group | No change to `/commands` | Lost if the tab closes or the WS drops while waiting; races between results |
| C. Propagation in the backend (`POST /entry-groups/:id/modify`) | One call per action | Duplicates the command pipeline and the per-broker queue; the panels already send lists |

## Data flow

```
New Trade / Quick order (mirror, ≥2 brokers)
  → POST /commands × N, each with the same groupId
  → backend: command_result ok + ticket → entry-groups store adds (broker, ticket) to groupId
  → on the group's 2nd member: row in entry_groups with a free palette colour
  → WS { type: "entry_groups", groups } to everyone
Positions/Orders (frontend): map posKey → { groupId, color }; star when ≥ 2 members are open
Edit / close / cancel / remove SL·TP / chart drag on a grouped entry
  → frontend expands it to the open members → sendCommands (one per broker, as today)
  → each command_result is collected by a batch → one summary toast (AC 7)
positions message from the pipe (per broker) → members whose ticket is no longer open are removed;
  a group with < 2 members left open is deleted → WS entry_groups
```

## Per-layer changes

### [db]
Migration `2026112xxxxxxx_entry_groups` (hand-written SQL):

```prisma
model EntryGroup {
  id        String             @id            // groupId generated by the frontend (^[A-Za-z0-9_-]{1,64}$)
  color     String
  createdAt DateTime           @default(now()) @map("created_at")
  members   EntryGroupMember[]
  @@map("entry_groups")
}

model EntryGroupMember {
  id      Int        @id @default(autoincrement())
  groupId String     @map("group_id")
  broker  String
  ticket  Int
  group   EntryGroup @relation(fields: [groupId], references: [id], onDelete: Cascade)
  @@unique([broker, ticket])
  @@map("entry_group_members")
}
```

`@@unique([broker, ticket])`: an entry belongs to one group at most.

### [backend]
- `routes/commands.ts`: optional `groupId` (same pattern as `id`), only allowed on opening actions. When the result is `ok` with a ticket → `addMember(groupId, broker, ticket)`. A late result (`late: true`) also counts.
- `store/entry-groups.ts` (new): in-memory cache + BD.
  - `addMember`: creates the group on its first member, with no colour yet. On the second member it picks the first colour of the palette not used by another group, or the least used one when all are taken.
  - `syncOpenTickets(broker, tickets)`: called from the `positions` handler in `index.ts`, like `syncColors`, but only when the set of tickets changes. It removes members that are no longer open and deletes groups with fewer than 2 members.
  - `removeMember(broker, ticket)`: take the entry out of its group (AC 10).
  - Every change → broadcast `entry_groups`.
- `routes/entry-groups.ts` (new, `requireAuth`): `GET /entry-groups` returns `[{ id, color, members: [{ broker, ticket }] }]`, and `DELETE /entry-groups/members` with body `{ broker, ticket }`.
- `ws`: `broadcastEntryGroups(groups)`, sent to everyone (like `positions`).
- Palette (constant in the backend): `#f5a623 · #3a7bd5 · #c77dff · #2ec4b6 · #ff6fa8 · #e8e8e8`. These are the approved star colours; they avoid green and red so they are not read as buy or sell.

**Safeguard against an empty `positions` message**: if the EA is reconnecting and sends an empty list for a broker that had open entries, the members are not removed until the same empty list arrives in two messages ≥ 5 s apart. Otherwise every group would be lost on an EA restart.

### [frontend]
- `lib/useEntryGroups.ts` (new): loads `GET /entry-groups` and listens to `entry_groups`. It exposes `groupOf(broker, ticket)` → `{ id, color, members }`, counting only the members that are open in the live snapshot (`useLivePositions`).
- `shared/ui/GroupStar` (new shared component): a 12 px SVG star with the group colour and `aria-label`.
- `OpenPositions`, `PendingOrders`, `PositionCard`, `OrderCard`: the star before the broker when the group has ≥ 2 open members. Hovering a row highlights the other members (`--tint-selected`).
- `lib/entryGroups.ts`: `expandToGroup(entry, livePositions)` → the entry plus its open siblings. It is applied in:
  - `BulkEditPanel`: the single-position edit opened from the table and from the chart. The typed SL/TP goes to every member; an untouched field keeps each one's own value (the current logic).
  - `EditOrderPanel`: price, SL and TP.
  - The close/cancel confirmation in Journal and in the chart. The message lists the brokers and lots, as in the mockup.
  - `ChartPage.onModifyPosition`: dragging SL/TP and removing SL/TP from the context menu.
- `BulkEditPanel` and `EditOrderPanel`: an info box "applies to N entries: brokers", the **Remove SL** and **Remove TP** buttons, **Take out of group** (`DELETE /entry-groups/members`), and the save button labelled "Save · N entries".
- `NewTradePanel` (mirror mode) and `QuickOrderConfirm`: with ≥ 2 commands they add `groupId: newCommandId()` to all of them.
- `lib/commandBatch.ts` (new): `trackBatch(label, ids→broker)`. `AppLayout` does not toast the individual `command_result`s of a batch. When all have arrived (or after 35 s) it shows one toast: "SL updated in 3 of 3", or "… 2 of 3 · FTMO — Invalid stops" as a warning.

No new dependencies.

## Risks
- **The tickets disagree with MT4**: if a broker's command result comes back without a ticket, that entry stays out of the group. This is visible because it has no star.
- **Empty `positions` on an EA restart**: covered by the safeguard above.
- **Same price on different brokers**: a SL that is valid on one broker can be rejected on another (stop level, spread). This is reported by the partial-failure toast, as agreed.
- **Two tabs editing at once**: each sends its own commands, as today; nothing new.
